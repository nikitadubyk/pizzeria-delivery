# План разработки Pizzeria Delivery

Обновлено: 6 сентября 2026 года.

Multi-tenant платформа доставки еды: каждый ресторан получает свою витрину, меню, оформление, сотрудников, настройки доставки и заказы. Данные ресторанов изолированы.

Этапы расположены в рекомендуемом порядке. Чекбоксы отмечаем после реализации и проверки критерия готовности. Предлагаемые решения для MVP можно пересматривать перед началом соответствующего этапа.

## Текущее состояние

- [x] Базовый super admin: управление ресторанами и пользователями ресторанов.
- [x] Модели Restaurant и User, роли SUPER_ADMIN, OWNER, EMPLOYEE.
- [x] Инфраструктура tenant-scoped доступа к Prisma.
- [x] Основа клиентской витрины и общие UI-компоненты.

Это исходная точка по текущему коду и завершённой работе, а не подтверждение готовности к production. Витрина пока использует статические данные; модели каталога, доставки и заказов ещё предстоит добавить.

## Первая рабочая версия — MVP

Владелец входит в админку, наполняет меню и настраивает ресторан. Покупатель открывает его сайт, собирает корзину и оформляет заказ. Заказ сохраняется и появляется в админке с уведомлением. Сотрудник принимает заказ и меняет статус, покупатель видит ход выполнения.

Предлагаемые границы MVP:

- Один ресторан на корзину и заказ.
- Категории, продукты, размеры пиццы и ингредиенты входят в MVP: выбор варианта, платные добавки и удаление разрешённых ингредиентов.
- Общая структура витрины с настраиваемыми названием, логотипом и основным цветом.
- Гостевой заказ без регистрации покупателя.
- Доставка по введённому адресу, фиксированная стоимость и минимальная сумма.
- Оплата наличными или картой при получении из разрешённых рестораном способов; для наличных — нужна ли сдача. Онлайн-оплата — отдельный следующий релиз.
- Стоп-лист товаров, размеров и добавок с быстрым отключением и возвратом в продажу.
- Пауза приёма заказов и отдельный switch «Большая загрузка»: предупреждение покупателю «Большая загрузка, ожидание дольше обычного», без ручного ввода дополнительного времени в MVP.
- Самовывоз наряду с доставкой.
- Уведомления в админке с дублированием каждого нового заказа в чаты VK и Telegram ресторана.
- Восстановление доступа и отключение сотрудников доступны администратору ресторана (OWNER).

Дополнительно согласовано для MVP:

- Собственный домен ресторана и базовое SEO на общей установке приложения: один сервер и одна PostgreSQL БД.
- Простые промокоды: скидка в рублях или процентах, срок действия, минимальная сумма и общий лимит применений.
- Небольшой отчёт: количество заказов, сумма завершённых заказов, средний чек, отмены и использования промокодов.
- Блок предложений дополнить заказ (допродажи) в MVP не включается.

Зависит от существующего super admin.

- [x] Реализовать вход, выход и проверку сессии владельца и сотрудника.
- [ ] Создать каркас админки: меню, заказы, настройки, доступ сотрудников.
- [ ] Дать администратору ресторана (OWNER) возможность инициировать восстановление доступа сотрудника своего ресторана и отключать его учётную запись.
- [ ] Предусмотреть восстановление собственного доступа администратора через подтверждённый контакт; конкретный канал определить при реализации.
- [ ] Для восстановления использовать одноразовое ограниченное по времени подтверждение; после смены пароля отзывать старые сессии. Отключение сотрудника должно прекращать доступ и по уже выданным сессиям.
- [x] Определять ресторан сотрудника по проверенной сессии, не по restaurantId из тела запроса.
- [x] Проверять активность пользователя и статус ресторана на сервере; определить поведение для SUSPENDED и ARCHIVED.
- [ ] Реализовать серверные проверки прав и соответствующую видимость действий в UI.
- [x] Проверить доступ на двух ресторанах, включая подмену идентификаторов в запросах.

Предлагаемые права для MVP:

| Роль | Доступ |
| --- | --- |
| SUPER_ADMIN | Управление ресторанами и их административными пользователями через существующий раздел |
| OWNER | Меню и стоп-лист, промокоды и отчёт, заказы, пауза и большая загрузка, оформление, доставка/самовывоз, настройка чатов, восстановление доступа и отключение сотрудников своего ресторана |
| EMPLOYEE | Просмотр и обработка заказов, изменение стоп-листа своего ресторана без права менять цены |

В MVP администратор ресторана восстанавливает доступ и отключает сотрудников. Создание сотрудников владельцем и более детальные разрешения — после MVP; существующее управление пользователями через super admin сохраняется. Доступ поддержки к операциям ресторанов следует проектировать отдельно и явно.

Готово, когда: владелец и сотрудник входят в свой ресторан, разрешённые действия работают, запрещённые отклоняются сервером, чужие данные недоступны. Администратор восстанавливает доступ сотруднику своего ресторана, а отключённый сотрудник теряет доступ, включая существующие сессии.

### Общий сервер и подключение доменов

Согласованная архитектура MVP: один сервер, одна установка Next.js и одна PostgreSQL БД pizzeria_delivery с tenant-изоляцией. Отдельная копия приложения или база для каждого ресторана не создаётся.

Схема запроса: домен ресторана → DNS на общий сервер → Nginx (HTTPS / reverse proxy) → общее приложение Next.js → определение Restaurant по домену → tenant-scoped запросы в общую БД.

Это обслуживание разных доменов одной системой: покупатель остаётся на домене ресторана. Nginx принимает запросы и проксирует их в приложение; сопоставление домена с restaurantId выполняется по данным приложения. Альтернативный reverse proxy допустим при сохранении этой архитектуры.

- [ ] Добавить tenant-owned модель привязки домена: нормализованное уникальное имя хоста, restaurantId, статус проверки/активации и признак основного домена. Уникальность домена глобальная, чтобы он не принадлежал двум ресторанам.
- [ ] Описать подключение DNS: A на IPv4 общего сервера, AAAA только при настроенном IPv6; для поддомена допустим CNAME на служебное имя. Проверять владение доменом до активации, например отдельной DNS TXT-записью.
- [ ] Настроить HTTPS-сертификаты для подключённых доменов, автоматическое продление и контроль ошибок. Активация витрины — после проверки домена, DNS и HTTPS.
- [ ] Проксировать разрешённые домены в один внутренний адрес приложения. Неизвестные хосты отклонять на reverse proxy и в приложении, не выбирать ресторан по умолчанию.
- [ ] Нормализовать имя хоста; доверять forwarded-заголовкам только от своего reverse proxy, который их перезаписывает. Закрыть прямой публичный доступ к порту приложения.
- [ ] Формировать абсолютные ссылки и SEO-адреса из проверенной записи основного домена; не использовать произвольный Host как доверенный адрес.
- [ ] Для www и других явно подключённых алиасов настроить перенаправление на основной домен; HTTP перенаправлять на HTTPS. Не выполнять перенаправления на непроверенные адреса.
- [ ] Админку ресторана и super admin для MVP размещать на служебном домене платформы. Tenant админки берётся из сессии; привязка домена витрины не меняет права сотрудника.
- [ ] Проверить изоляцию кеша, файлов, корзин и cookie между ресторанами и доменами. Автоматический перенос локальной корзины между разными доменами не входит в MVP.
- [ ] Предусмотреть смену/отключение домена, очистку кеша привязки и повторную проверку владения перед новым назначением. Зарезервировать служебные домены платформы.

Развёртывание на одном сервере подходит как стартовая схема. Его отказ затронет все рестораны, поэтому в этапе 7 обязательны мониторинг и резервные копии вне этого сервера с проверкой восстановления. Масштабирование можно проектировать после пилота.

- [ ] Объединять позиции только при совпадении продукта, варианта, удалённых ингредиентов и добавок с их количеством. Разные конфигурации одной пиццы — разные строки.
- [ ] Позволять редактировать конфигурацию из корзины, показывать размер, состав изменений и доплаты.

- [ ] Изоляция корзины по ресторану: товары разных ресторанов не смешиваются.
- [ ] Проверка наличия и актуальных цен перед checkout с сообщением об изменениях.
- [ ] Пустое состояние, ограничения количества и удобное управление с телефона.

Готово, когда: покупатель собирает корзину, возвращается к ней после перезагрузки и видит актуальные условия перед оформлением.

### 4.1. Простые промокоды

Зависит от каталога и корзины; завершить вместе с серверным созданием заказа на этапе 5.

- [ ] Добавить tenant-owned промокоды и учёт применений. OWNER создаёт, редактирует и отключает промокоды своего ресторана.
- [ ] Настройки: код, скидка в рублях или процентах, начало/конец действия, минимальная сумма товаров и общий лимит применений. Нормализация кода и уникальность — внутри ресторана.
- [ ] Один промокод на заказ; в MVP нет суммирования акций, подарков, бонусов и условия «только первый заказ».
- [ ] Скидка применяется к сумме товаров с выбранными добавками, не к доставке, и не превышает сумму товаров. Минимальную сумму промокода и доставки проверять до скидки; округление определить единообразно в копейках.
- [ ] В корзине показывать результат применения и понятную причину отказа; при изменении состава пересчитывать скидку.
- [ ] На сервере повторно проверять условия и атомарно учитывать общий лимит вместе с созданием заказа. Параллельные запросы не превышают лимит, повтор одного запроса не расходует его повторно.
- [ ] Сохранять код, условия и сумму скидки снимком в заказе. Для MVP применение расходуется при создании заказа и не возвращается автоматически при отмене; явно показать это правило владельцу.

Готово, когда: оба вида скидки рассчитаны правильно, истёкший или чужой промокод отклоняется, лимит защищён от параллельных применений, старые заказы сохраняют свою скидку после изменения кода.

## 5. Доставка, самовывоз и создание заказа

Зависит от этапа 4.

- [ ] Настройки доставки: доступность, фиксированная стоимость, минимальная сумма, ориентировочное время, часы приёма заказов и часовой пояс ресторана.
- [ ] Добавить два независимых переключателя ресторана: «Приём заказов приостановлен» и «Большая загрузка». Пауза запрещает новые заказы на доставку и самовывоз на сервере; большая загрузка только предупреждает и не блокирует оформление. Существующие заказы продолжают обрабатываться.
- [ ] Сохранять оба состояния в БД для конкретного ресторана. При оформлении повторно проверять паузу, сохранять признак большой загрузки в заказе, чтобы позднее выключение switch не меняло условия, показанные при оформлении.
- [ ] Добавить выбор «Доставка / Самовывоз» из включённых рестораном способов. Для самовывоза показывать адрес точки и ориентировочное время готовности, не требовать адрес покупателя, не начислять доставку и не применять минимальную сумму доставки.
- [ ] В MVP описать обслуживаемую территорию текстом; неподходящий адрес может отклонить оператор. Автоматические зоны — этап 9.
- [ ] Checkout: имя, телефон, адрес, квартира/подъезд/этаж/домофон при необходимости, комментарий.
- [ ] Настройки оплаты при получении: наличные и/или карта через терминал ресторана, отдельно для доставки и самовывоза. Показывать только включённые способы и проверять выбор на сервере.
- [ ] Для наличных добавить «Без сдачи / Нужна сдача» и сумму, с которой подготовить сдачу; проверять, что она не меньше итога заказа. Сохранять выбор и показывать сотруднику в карточке.
- [ ] Выбор карты при получении не означает подтверждение оплаты и не требует ввода реквизитов карты на сайте.
- [ ] Добавить модели заказа и позиций отдельным доменом Prisma; сохранять способ оплаты, сведения о сдаче и снимок промокода/скидки.
- [ ] Сохранять снимок названий, размера/теста, базового состава, удалённых ингредиентов, добавок и их цен, количества, контактов, способа получения, адреса доставки или точки самовывоза и стоимости доставки. Изменение меню не меняет историю заказов.
- [ ] Проверять на сервере ресторан, товары, варианты, допустимость и количество добавок/удалений, доступность, цены, часы приёма и условия доставки; итог рассчитывать по данным БД.
- [ ] Создавать заказ и позиции атомарно; защитить повторную отправку от дублей.
- [ ] Показывать подтверждение только после сохранения, с номером и ссылкой на статус.
- [ ] Защитить публичный просмотр заказа непредсказуемым токеном или другим проверяемым механизмом: одного последовательного номера недостаточно.
- [ ] Ограничить частоту отправки заказов и исключить утечку контактов через публичные ответы и логи.

Готово, когда: гостевой заказ сохраняется с правильной суммой, подмена цены не работает, повтор запроса не создаёт дубль, чужой заказ нельзя получить подбором номера. Самовывоз оформляется без адреса покупателя и платы за доставку; пауза блокирует новые заказы, switch большой загрузки показывает предупреждение, но позволяет заказать.

## 6. Обработка заказов и уведомления

Зависит от этапа 5.

- [ ] Список заказов ресторана: новые сверху, фильтры по статусу и дате.
- [ ] Карточка: размер и тесто каждой пиццы, заметные пометки «убрать» и «добавить», количество, сумма, способ оплаты, контакты, адрес, комментарий и время создания.
- [ ] Переходы доставки: NEW → ACCEPTED → PREPARING → OUT_FOR_DELIVERY → DELIVERED.
- [ ] Переходы самовывоза: NEW → ACCEPTED → PREPARING → READY_FOR_PICKUP → PICKED_UP. Показывать способ получения в списке и карточке; не допускать переходов от другого способа получения.
- [ ] Определить допустимые отмены; сохранять причину и историю смены статусов с исполнителем.
- [ ] Проверять переходы на сервере, учитывать одновременную работу сотрудников.
- [ ] Добавить индикатор новых заказов и уведомления; звук — с возможностью включения пользователем.
- [ ] Дублировать уведомление о каждом сохранённом новом заказе в оба чата ресторана: VK и Telegram. Отправка работает независимо от открытой админки.
- [ ] Добавить для OWNER настройку и проверку подключения чатов VK и Telegram своего ресторана. Секреты хранить на сервере; предусмотреть тестовое уведомление при подключении.
- [ ] В уведомлении указывать ресторан, номер, сумму, способ получения и ссылку в защищённую админку; полные контактные данные доступны в карточке после авторизации.
- [ ] Сохранять задания уведомлений надёжно вместе с заказом (например, transactional outbox), отправлять в фоне, независимо повторять неудачные попытки VK и Telegram, показывать ошибки доставки администратору.
- [ ] Учитывать повторную обработку задания и возможные дубли при неопределённом ответе внешнего сервиса; уведомление всегда содержит один и тот же номер заказа. Сбой канала не откатывает заказ и не блокирует второй канал.
- [ ] Для MVP использовать периодическое обновление списка; после переподключения получать пропущенные заказы из БД.
- [ ] Обновлять статус на странице покупателя, включая понятное сообщение при отмене.
- [ ] Проверить сценарий: админка закрыта во время заказа, затем открыта — заказ виден и доступен для обработки.

Готово, когда: ресторан принимает заказ и доводит его до доставки или отмены, покупатель видит актуальный статус. Новый заказ дублируется в VK и Telegram своего ресторана, сбои каналов видны и повторяются независимо. Самовывоз проходит до выдачи покупателю. Сохранность заказа не зависит от уведомления.

### 6.1. Небольшой отчёт для владельца

Зависит от заказов, статусов и промокодов; входит в MVP.

- [ ] Один экран OWNER с выбором периода в часовом поясе ресторана: количество созданных заказов, завершённых и отменённых, сумма завершённых заказов, средний чек и использования промокодов.
- [ ] Для MVP выбирать заказы по дате создания в периоде и считать по их текущему статусу. Завершённые — DELIVERED и PICKED_UP; объяснить, что показатели прошлого периода могут изменяться при смене статусов.
- [ ] Сумма завершённых заказов — итог после скидки с доставкой; средний чек — эта сумма, делённая на число завершённых заказов. При отсутствии завершённых заказов показывать 0. Это операционный отчёт, не подтверждение фактического поступления денег.
- [ ] По промокоду показывать число созданных заказов с ним, число завершённых и сумму скидок в завершённых заказах; отмены не считать завершёнными продажами.
- [ ] Проверить tenant-изоляцию, границы дат, скидки и самовывоз на наборе заказов с заранее известным результатом.

Готово, когда: владелец видит понятные показатели своего ресторана за период, расчёт сходится с заказами и не включает чужие данные.

## 7. Проверка и запуск MVP

Зависит от этапов 1–6. Здесь заканчивается первая рабочая версия.

- [ ] Пройти полный сценарий на двух ресторанах: меню → витрина → корзина → заказ → уведомление → доставка.
- [ ] Проверить права и tenant-изоляцию, повторы запросов, недоступные товары/варианты/добавки, разные конфигурации в корзине, подмену доплат, изменение меню после заказа, закрытый ресторан и сетевые ошибки.
- [ ] Проверить доставку и самовывоз, включение/выключение паузы и большой загрузки, стоп-лист после добавления товара в корзину.
- [ ] Проверить уведомления в обоих чатах при закрытой админке, недоступность одного канала, повторную отправку и отсутствие сообщений в чатах другого ресторана.
- [ ] Проверить восстановление доступа, истёкшее/повторное подтверждение, отзыв сессий и запрет управления сотрудником чужого ресторана.
- [ ] Проверить два собственных домена на одной установке: DNS, HTTPS и продление, неизвестный Host, изоляцию кеша, canonical, sitemap, preview и отсутствие индексируемых дублей.
- [ ] Проверить промокоды, конкурентное исчерпание лимита, итог со скидкой, выбор наличных/карты и сведения о сдаче; сверить отчёт с контрольными заказами.
- [ ] Проверить мобильный checkout, клавиатурную навигацию и сообщения об ошибках.
- [ ] Подготовить production-конфигурацию, миграции, хранилище изображений, резервные копии БД и необходимых файлов вне основного сервера и проверить восстановление.
- [ ] Настроить сбор ошибок и наблюдение за неудачным созданием заказов без утечки персональных данных.
- [ ] Подготовить необходимые тексты для покупателей и правила хранения их данных перед публичным запуском.
- [ ] Выполнить тесты, lint и build; провести пилот с одним рестораном.

Готово, когда: ресторан может принимать реальные заказы с оплатой при получении, полный сценарий и изоляция данных проверены.

## 8. Онлайн-оплата

Зависит от стабильного цикла заказов, этапы 5–7. Если карта обязательна для первого запуска, перенести этот этап перед публичным запуском MVP.

- [ ] Выбрать провайдера, например ЮKassa, после проверки актуальных условий и возможностей интеграции.
- [ ] Определить получателя платежей: отдельный аккаунт каждого ресторана или согласованная схема через платформу. До этого не фиксировать платёжную архитектуру.
- [ ] Добавить модель платежа; отделить состояние оплаты от статуса приготовления/доставки.
- [ ] Создавать платёж на сервере по сохранённой сумме заказа, хранить секреты вне публичных настроек.
- [ ] Подтверждать оплату проверенным серверным событием провайдера, а не возвратом браузера на страницу успеха.
- [ ] Обрабатывать повторные и запоздавшие события идемпотентно, проверять связь платежа с рестораном и заказом.
- [ ] Определить момент передачи заказа кухне, срок ожидания оплаты и поведение при поздней оплате отменённого заказа.
- [ ] Реализовать неуспешную оплату, повторную попытку, сверку зависших платежей и возврат при отмене.
- [ ] Уточнить требования к чекам и возвратам для выбранной схемы, проверить интеграцию в тестовом окружении провайдера.

Готово, когда: успешная/неуспешная оплата, повтор webhook и возврат не приводят к неверным суммам или дублированию заказов.

## 9. Зоны доставки

Зависит от этапа 5; не зависит от онлайн-оплаты.

- [ ] Выбрать картографический сервис и представление зон: радиус или полигоны.
- [ ] Добавить зоны ресторана с ценой, минимальной суммой и ориентировочным временем.
- [ ] Добавить подсказки адреса, координаты и серверную проверку попадания в зону.
- [ ] Определить приоритет пересекающихся зон и поведение на границе.
- [ ] Запрещать оформление вне зоны с понятным объяснением, предусмотреть недоступность сервиса карт.
- [ ] Сохранять рассчитанные условия в заказе: изменение зон не меняет старые заказы.

Готово, когда: стоимость и доступность доставки рассчитываются по адресу, проверены границы и адреса вне территории.

## 10. Развитие после MVP

Выбирать по обратной связи пилотного ресторана; это не обязательства первого релиза.

- [ ] Сложные конструкторы: пицца из половинок, наборы с выбором состава и комбо. Базовые размеры и ингредиенты уже входят в MVP.
- [ ] Заказ на выбранное время; обычный самовывоз уже входит в MVP.
- [ ] Создание сотрудников владельцем, детальные разрешения, журнал административных действий. Восстановление доступа и отключение сотрудников уже входят в MVP.
- [ ] Дополнительные каналы уведомлений и эскалация непринятых заказов. Дублирование в VK и Telegram с повторными попытками уже входит в MVP.
- [ ] Клиентские аккаунты, адреса, история и повтор заказа — отдельный tenant-owned домен Customer, без клиентской роли в UserRole.
- [ ] Курьеры, назначение доставки и рабочий экран курьера.
- [ ] Сложные акции, комбо и лояльность; простые промокоды уже входят в MVP.
- [ ] Расширение темы и управление баннерами; собственные домены и базовое SEO уже входят в MVP.
- [ ] Расширенная аналитика и популярные товары; небольшой отчёт по заказам, суммам и промокодам уже входит в MVP.
- [ ] Развитие super admin: состояние ресторанов, аудит и явно разрешённый доступ поддержки.

## Что рекомендуется до первой коммерческой продажи

В обязательный MVP согласованы размеры и ингредиенты, стоп-лист, пауза приёма заказов, switch большой загрузки, самовывоз, уведомления в VK и Telegram, восстановление доступа и отключение сотрудников администратором ресторана. Также согласованы собственные домены на одном сервере и общей БД, базовое SEO, простые промокоды, небольшой отчёт и выбор оплаты наличными/картой при получении. Допродажи исключены из MVP. Эти задачи включены в этапы 1–7. Ниже остаются дополнительные рекомендации, ещё не согласованные как обязательные.

| Приоритет | Возможность | Зачем нужна / куда включить |
| --- | --- | --- |
| До платного запуска | Подтверждение рестораном и понятное ожидаемое время; связь с рестораном и обработка отмены | Покупатель понимает, принят ли заказ и сколько ждать; этапы 5–6 |
| До платного запуска | Подключение ресторана, заполнение меню, тестовый заказ и понятный канал поддержки | Продаётся готовый процесс запуска; этап 7. Первые подключения можно делать вручную |
| До платного запуска | Поиск заказа по номеру/телефону в админке, история действий и печатное представление для кухни | Разбор звонков и ошибок, работа кухни; этап 6 |

Не стоит откладывать проверку tenant-изоляции, серверный расчёт цены, защиту от дублей, сохранение состава заказа, восстановление БД и мониторинг ошибок ради дополнительных визуальных функций.

Первый платный пилот предлагается ориентировать на независимую пиццерию с одной точкой, которая согласна обрабатывать заказы в отдельной админке. Готовность к продаже проверяется реальной сменой: сотрудник получает, готовит и закрывает заказы без участия разработчика; ошибки и отмены обрабатываются предсказуемо.

Личный кабинет покупателя, бонусы, приложение курьера, сложные акции, складской учёт и конструктор произвольных страниц можно оставить после такого пилота.

Ориентир для рекомендаций: [описание сайта доставки iiko](https://blog.iiko.ru/kak-prodvigat-dostavku-edy) — актуальность меню и стоп-листов, стоимость и время доставки по адресу. Приоритеты выше — проектное предложение, а не универсальные требования рынка.

## Общие правила реализации

- Новые бизнес-модели ресторана имеют обязательные restaurantId, связь с Restaurant и индекс, начинающийся с restaurantId.
- Перед добавлением моделей и доступа к БД читать [prisma.md](../prisma/prisma.md). Проверять принадлежность связанных сущностей ресторану, включая вложенные операции.
- Ресторанные операции используют getRestaurantDb(restaurantId), межресторанные административные — getSuperAdminDb(authenticatedUserId). systemDb не используется в обычных обработчиках запросов.
- Права, цены, доступность и переходы статусов проверяются сервером.
- Проверять бизнес-инварианты и tenant-изоляцию. При изменении приложения или Prisma выполнять lint/build и релевантные тесты.
- Перед изменением Next.js API и маршрутизации читать соответствующие руководства в node_modules/next/dist/docs/.
- Использовать Mantine для интерактивных компонентов, Tailwind для компоновки, общие токены для темы.

## Ближайшая задача

Текущий объём — только вход и первая защищённая страница /admin. Вход по email или телефону и паролю; restaurantId определяется из найденного пользователя и сохраняется в подписанной сессии. Поле slug не требуется. Разделы меню, заказов, настроек и сотрудников пока не реализуются.
